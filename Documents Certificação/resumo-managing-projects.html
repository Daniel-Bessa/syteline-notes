Managing Projects
Resumo de estudo — Workbook de certificação (CSI v10.18)
Resumo
🎯 Visão geral do módulo Projects ▶
•Projects é uma ferramenta de gestão de custos que permite capitalizar custos de projetos grandes e demorados — desde contratos governamentais até tracking interno de melhorias, mudanças de instalações ou projetos de software.
•Estrutura hierárquica: Project → Project Tasks (etapas necessárias) → Project Resources (materiais/mão-de-obra/outros necessários para cada task).
•Permite atribuir e controlar custos planeados e compromissos por projeto, task e recurso, gerindo material, labor, overhead e G&A (general & administrative) — a um nível superior ao de um job order.
•Regra de custo: se um recurso não está ligado a job orders e o item existe na tabela Items, precisa de Cost Type = Actual para que os custos reais sejam postados ao projeto; se o Cost Type for Standard, é sempre emitido ao custo unitário standard, mesmo que o recurso esteja ligado a uma linha de PO.
•Interfaces do Projects com o resto da aplicação: Estimating, Customer Order Entry, Accounts Receivable, Payroll, Accounts Payable, Purchasing, Job/Service Orders e Planning.
•Formas de "Percent of Completion" (nível de projeto e de task) permitem comparar custo real acumulado com o custo forecast do projeto.
💡 Manipulações de custo/despesa como WIP relief, revenue recognition e invoicing ocorrem diretamente a partir do próprio projeto.
•Cursos pré-requisito úteis para contexto: Navigating the User Interface, Foundation 101, Using Job Orders, Costing Foundation, Using Purchase Orders and Requisitions, Using Accounts Payable, Using Accounts Receivable.
⚙️ Configuração base: Parameters, Cost Codes e Milestone Events ▶
•Project Parameters — Default tab: define como o módulo Projects funciona globalmente; contém o Project Prefix (numeração automática de projetos) e o Estimate Prefix (numeração automática de projetos estimados, útil para identificar rapidamente todos os novos projetos com o mesmo prefixo alfanumérico/numérico ao rever relatórios).
•Project Cost Codes: código definido pelo utilizador para classificar custos em Labor, Material ou Other (Cost Class). Determina qual conta de projeto é debitada/creditada quando transações são postadas.
•Cada cost code define se overhead e/ou G&A overhead devem ser calculados como % do custo (checkboxes Calculate Overhead / Calculate G&A). Um cost code com Cost Class = Labor permite ainda definir um Default Cost Rate e Default Budget Rate (usados ao adicionar cost codes/orçamentos no Estimate Projects e no Estimate Project Tasks, tab % Complete).
•Product Codes — Project tab: define as contas de ativo usadas para lançamentos contabilísticos quando transações de inventário afetam um projeto. O campo Cost Code aqui é o cost code default para itens atribuídos a esse Product Code (ex.: material de job cross-referenciado a um projeto).
💡 A nova norma GAAP/IFRS (2018) exige reconhecimento de receita de forma consistente com a transferência de bens/serviços — os Project Milestone Events ajudam a lembrar os utilizadores de processar Revenue e Invoice Milestones quando tempo decorre ou custos/horas se acumulam.
•3 tipos de evento: Project Completion Event, Task Completion Event e Performance Obligation Event.
  1. 1No form Publication Subscribers, subscrever as publicações Project Completion Alert, Project Task Completion Alert e Project Obligation Completion Alert.
  2. 2No form Project Obligation Group Cost Codes, definir grupos de obrigação e os cost codes associados (depois de atribuído a um evento, o grupo não pode ser eliminado).
  3. 3No form Project Milestone Events, configurar os grupos de campos Project Completion, Task Completion e Performance Obligation por projeto/task.
  4. 4Definir o tipo de Project MS: Cost, Time Elapsed, Hours ou Percent Complete. Time Elapsed cria uma background task para disparar o evento (em vez do Next MS Threshold).
  5. 5Marcar Recurring se o limiar se repetir sempre igual (gera automaticamente um novo evento após cada ocorrência — não disponível com Time Elapsed).
⚠️ Se for necessário recalcular totais acumulados após adicionar/remover cost codes de projeto, usar o botão Recalculate Obligations — só depois de terminar todas as modificações.
📐 Estimate Projects (Lição 2) ▶
•Um Estimate Project é criado manualmente ou por cross-reference de uma linha de encomenda estimada. O Status é sempre "Estimate" (todo o cálculo de custos exige este status).
•Se não houver cliente associado, o Type tem de ser "Non-Billable".
•Campos obrigatórios no General tab: Product Code, Overhead Rate, G&A Rate. Campo opcional Estimate Project referencia outro projeto estimado.
•Estimate Project Tasks subdividem o projeto estimado; Start Date e End Date são obrigatórios; o campo Order mostra a customer order/linha se houver cross-reference.
•Estimate Project Resources: identifica recursos necessários por task (Item, Type — Material/Fixture/Tool/Other, Cost Code, Qty, U/M, Warehouse, Due Date). O campo Source indica a origem: Inventory, Purchase Order, Job Order ou Purchase Order Requisition.
•Tab Cost permite entrar/ver: Material Cost, Labor Cost, Fixed Overhead Cost, Variable Overhead Cost, Outside Cost, e os Accum Values (valores reais já emitidos ao projeto).
•Estimate Project Tasks — % Complete tab: mostra Forecast Cost e Cost to Complete (editáveis) por cost code, não a % física do projeto concluído.
💡 Fórmulas recorrentes em vários grids (Estimate Projects, Projects, Project Tasks):
Cost to Complete = Forecast Cost − Actual Cost
% Complete = Actual Cost ÷ Forecast Cost (se Forecast Cost = 0, o % Complete mostra 100%)
•O overhead e G&A calculados aparecem em baixo do grid, com base nas % definidas no Estimate Projects form; os cost codes vêm dos recursos entrados no Estimate Project Resources.
🏗️ Projects — estrutura principal (Lição 3) ▶
•Project Parameters — Evaluation tab: define os limiares Schedule Variance e Cost Code Variance (Lower/Upper Deviation %) usados para avaliar o estado de controlo do projeto no form Project/Job Accumulated Cost by Period.
•Semáforo de estado: ✅ verde = "In Control"; ⚠️ amarelo = ultrapassou o Lower Deviation % (em perigo); ❌ vermelho X = ultrapassou o Upper Deviation % (fora de controlo).
•Priority Level: valor numérico (quanto mais baixo, maior prioridade) que decide qual indicador mostrar quando Schedule Variance e Cost Code Variance têm o mesmo nível de aviso (ex.: os dois "vermelhos" ao mesmo tempo).
•Project Types — 3 categorias de pricing: Fixed Price (valor de contrato acordado, faturação baseada em receita planeada), Calculated (faturas baseadas nos custos reais acumulados) e Non-Billable (sem receita associada).
•Projects form (Header): Project (auto-numerado via Project Prefix), Customer — obrigatório para posting de invoice milestones; se não tiver cliente, o Type tem de ser Non-Billable.
•Projects — General tab (campos-chave): Status (Active — acumula custos / Inactive — bloqueia acumulação / Complete — já não ativo); Product Code (obrigatório); Late Alert (assinala recursos projetados ou já atrasados); Track Changes (checkbox irreversível — uma vez ligado não pode ser desligado, requer "Tracking" ativo no Project Types); Change / Change Status (read-only, ligados ao Project Change Orders — ver Apêndice D); Detail (tree view de tasks/recursos).
⚠️ Trocar o Project Type não desliga o Track Changes, mesmo que o novo tipo não tenha Tracking ativo.
•Projects — % Complete tab: só leitura (breakdown por cost code de Actual, Forecast, Budget, Cost to Complete); ajustes só se fazem no Project Tasks form, % Complete tab.
•Project Tasks: numeração auto-incrementa de 10 em 10 (pode ser sobrescrita); mesmos Status e Late Alert que o Projects form.
•Project Resources: igual ao Estimate Project Resources, mas ao nível de projeto real. Tab Source permite cross-reference a Inventory, Purchase Order, Job Order, Purchase Order Requisition, SRO, ou Transfer Order (multi-site: transferir entre armazéns/sites).
•Copy Projects: copia um projeto, projeto estimado ou projeto de histórico para um novo/existente. Ao converter um Estimate Project em Project, copia também as Estimate Project Tasks, Estimate Project Resources, Revenue Milestones e Invoice Milestones.
💡 Relatórios úteis do módulo: Project Margin Analysis Report, Project Transactions Report, Project Variances Report (Master Explorer > Modules > Project > Reports).
📦 Planeamento e transações de projeto (Lições 4 e 5) ▶
•Planning — Project Resources: qualquer item existente na tabela Items pode ser planeado via MRP; a Start Date da task é a data usada como necessidade (requirement) para o planeamento.
•Material Planner Workbench: alternativa ao MRP/APS completo — considera procura e reabastecimento em todos os armazéns e cria ordens de fornecimento planeadas sempre que o stock disponível cai abaixo do safety stock. Pode ser convertido em purchase orders, requisições, jobs, MPS orders ou transfer orders.
•Planning Detail: mostra transações individuais criadas após correr APS, MRP ou MPS Processor; indica o dia exato de cada necessidade; útil sobretudo em grid view para confirmar planned orders.
•Project Labor Transactions: aplica o custo de mão-de-obra a um projeto/task específico; o Project Rate vem do Mfg Reg Rate no Employee form (tab Rates and Taxes). O custo real só é atualizado depois de as transações serem postadas.
•Post Project Labor Transactions: "Print + Process" mostra as transações prontas a postar (sem efeito contabilístico); "Commit + Process" efetivamente publica no Project Control Ledger Distribution Journal.
💡 Exemplo de lançamento de labor postado: débito em Project Account – Labor/OH/G&A; crédito em Direct Labor Expense, Fixed Labor Overhead Applied, Variable Labor Overhead Applied e Project Parameter Account – Applied OH/G&A.
•Employees — General tab: o campo Department é obrigatório e determina as contas de overhead usadas no posting de labor.
•Departments: define as taxas fixas e variáveis de overhead e as contas GL usadas quando labor é postado a um projeto.
•Project Resource Transactions: emite custo e quantidade de recursos ao projeto; o cost code é obrigatório para postar. Resultado visível no Project Resources form, tab % Complete.
💡 Item inventariado: débito Project Account Material/OH/G&A, crédito Inventory Material + Project Parameter Applied OH/G&A.
Item não-inventariado: débito igual, mas crédito na conta de despesa (Expense Account) em vez de Inventory.
🛒 Purchasing, Job Orders e Vouchering (Lições 6, 7 e 8) ▶
•Cross-reference de PO a Project Resource (tab Source): permite capturar o custo do purchase order no projeto. Ao receber o PO, o sistema emite automaticamente o recurso ao projeto — o item entra primeiro em inventário e depois é emitido.
⚠️ Recomenda-se cost method LIFO para o item, para evitar que o custo de receção seja diferente do custo emitido ao projeto. Se Cost Type = Standard, é sempre emitido ao custo unitário standard.
•Purchase Order Receiving: materiais recebidos por PO ligado a projeto/task geram lançamentos duplos — no Purchasing Ledger Distribution Journal (Inventory Material / Vouchers Payable) e, em espelho, no Project Control Ledger Distribution Journal (Project Account Material/OH/G&A / Inventory Material + Applied OH/G&A).
•Job Orders cross-referenciados (Source tab = Job): quando um recurso é cruzado com um job, perde a visibilidade de cost type/method — porque um job nunca entra em inventário ao completar, e todos os custos ficam ao nível do projeto.
•Job Orders form: tab Scheduling referencia Item, Item Description, Released; tab References referencia Project, Project Task, Customer, Due Date. No Project Cost Roll Up, os cost codes vêm do Work Centers form e do Product Codes form (tab Project).
•Job Material/Labor Transactions: custo de material/labor de um job capitalizado no projeto (cost code obrigatório). O WIP líquido de um job cross-referenciado a um projeto deve ser sempre zero nos distribution journals.
•Post Job Transactions: reconhece os custos do job e acumula-os no projeto. Não há transações de inventário ao completar itens de job ligado a projeto, porque tudo fica ao nível do projeto.
•A/P Vouchers and Adjustments: captura despesas diversas (ex.: despesas de viagem) acumuladas num projeto; liga-se ao projeto/task via Voucher Adjustment Distribution, onde project, task e cost code são obrigatórios — o cost code determina a conta de projeto usada no lançamento.
•A/P Voucher Posting: depois de postado, gera uma única entrada no Project Control Ledger Distribution Journal com o overhead/G&A calculado a partir do valor do voucher.
🚚 Shipping e Work in Process / WIP (Lições 9 e 10) ▶
•Project Resource Shipping: permite enviar produto diretamente do projeto, sem passar pela customer order. Qty to Ship = quantidade emitida ao projeto − quantidade já enviada.
💡 Como o custo já está atribuído ao WIP, o processo de shipping não gera lançamentos contabilísticos — serve apenas para saber se o material está no site da empresa ou do cliente. Para devolver a stock (antes de faturar), basta registar quantidade negativa.
•Project Packing Slip / Project Pre-Ship Packing Slip / Project Advance Ship Notices: documentos gerados a partir do projeto ou do packing slip; opção Recalculate atualiza os totais faturáveis.
•Project Parameters — General tab: define o WIP Relief Method default, com 3 opções: Manual, Shipment, Revenue Recognition (pode ser alterado por task individual no Projects form, WIP Relief tab).
•Distribution Accounts (por Product Code): definem as contas COGS necessárias para aliviar o WIP do projeto.
•Projects — WIP tab: 5 contas de custo (Material, Labor, Other, Overhead, G&A). WIP Relief tab: mostra o método, a Start WIP Relief date e as contas de relief; mapeamento para COGS: Material→Material, Labor→Labor, Other→Outside Services, Overhead→Variable Overhead, G&A→Fixed Overhead.
ManualExige uma Start Date manual; o relief corre a partir dela via Print/Post Project WIP Relief.
ShipmentDispara quando uma customer order line cross-referenciada é enviada; grava Start Date automaticamente.
Revenue RecognitionWIP só é aliviado ao processar o Print/Post Project Revenue Milestones — e só ao nível de projeto, nunca de task.
•Print/Post Project WIP Relief: Print Level (resumo por projeto ou por task) + Post Level (No posting / Project / Task). Não é necessário correr se o método for Revenue Recognition.
•Project WIP Adjustments: ajusta WIP ao nível de task nas 5 contas; depois é preciso correr o Print/Post Project WIP Relief para concluir o processo.
💡 Roll Up Project Cost (utilitário) recalcula/atualiza os totais de custo (e opcionalmente receita planeada) — correr sempre antes de conferir WIP ou de criar revenue milestones. Net WIP = Total Cost − Total WIP Relieved.
🗂️ WBS, Revenue Recognition e Invoicing (Lições 11, 12 e 13) ▶
•Work Breakdown Structures (WBS): agrupa vários projetos/tasks para reporting a um nível superior ao do projeto (ex.: contrato governamental com muitos projetos). Nome alfanumérico + descrição opcional.
•Status Planned: transações não podem ser entradas nas tasks associadas. Status Released: transações permitidas (Project Resource, Labor, WIP Relief, Invoice/Revenue Milestone posting, Job Material/Labor Transaction, PO Receiving, A/P Voucher posting).
•Tab WBS mostra árvore expansível Project → Task → Resource (recursos não têm filhos).
•Revenue Recognition — Project Parameters (General tab): Revenue Milestone Calculation (Manual / % Over Cost / % Of Project Revenue / Custom), Cost Calculation, Revenue Milestone Auditing, Multi-Requirement Tasks (Never/Sometimes/Always), Unbilled A/R Account.
•Revenue Milestones: processo de 2 passos — Nominate depois Post. Milestone Cost Calculation: Manual, % of Project Cost, % of Milestone Revenue, % of Milestone Requirements, Unrelieved Cost, Custom. Milestone Revenue Calculation: Manual, % Over Milestone Cost, % of Project Revenue, Custom.
•Requirements tab: checkbox Required Complete selecionado = requisito "hard" (bloqueia a nomeação até estar cumprido); desmarcado = "soft" (apenas aviso, permite continuar).
•Revenue Milestone Nomination: botão Auto Nomination verifica automaticamente todos os requisitos; existem 2 botões Calculate Cost/Revenue (um para Planned, outro para Actual).
💡 Exemplo de lançamento ao postar Print/Post Project Revenue Milestones: débito COGS – Material / crédito Project Account – Material (Project Control Ledger); e débito Unbilled A/R Account / crédito Sales Revenue (Accounts Receivable Distribution Journal). Este processo reconhece receita e alivia WIP ao mesmo tempo.
•Project Retention Codes (sobretudo contratos governamentais): retêm % da fatura até certa fase de conclusão. Billing Method: Individual (retenção separada em cada fatura) vs Total (retido e só faturado no fim do projeto).
•Projects — Invoicing tab: Auto Nominate, Invoice Method — Manual vs Revenue Recognition (este último cria automaticamente um Invoice Milestone quando um Revenue Milestone é postado, com valor igual à receita real), Invoice Terms, Retention Code/Terms, Exchange Rate (multi-moeda).
•Invoice Milestones: mesmo processo de 2 passos (Nominate + Post); checkbox Ignore Retention on Invoice para milestones não sujeitas a retenção.
⚠️ O Post Project Invoice Milestones NÃO cria lançamentos contabilísticos — é só relatório. Os lançamentos reais só acontecem quando as Invoices, Debit and Credit Memos são postadas no A/R Distribution Journal.
•Post Project Retention Invoice: cria a fatura final de retenção pendente, chamada Liquidation Invoice.
•Invoice Posting: cria lançamentos no A/R Distribution Journal (não afeta o Project Control Ledger). Para revenue recognition, podem ser necessários ajustes manuais de A/R.
👥 Payroll, Project Manager Home e MS Project (Lições 14, 15 e 16) ▶
•Generate Payroll: checkbox Summarize Project Transactions resume as horas de mão-de-obra já postadas diretamente num projeto.
⚠️ O Project Manager Home não está incluído em nenhum grupo de permissões por default — o administrador do sistema precisa de dar autorização explícita para aceder a este form.
•Ícones de atalho no topo: MS Project, Word, Excel, Outlook, Bing, Infor 365 Support (desativados se a aplicação não estiver instalada).
•Dashboard tab: secção My Stats com links para Alerts, Tasks e Inbox.
•Navigator tab (maioria read-only, filtrável por Project Manager): Hot List (recursos em atraso/planeamento), Projects (filtros Past Due/Late Resources/Active/Inactive/Complete/All), WBS, Jobs, Purchase Orders, Shipping, Transactions, Exceptions, Cost Code Analysis, Costing Activity, Period Costs, Accumulated Costs.
•Tasks tab: Alerts (Past Due Projects, Past Due Project Tasks, Estimates to Expire — número a vermelho se > 0, a verde se = 0), Tasks e Inbox.
•Flow tab: fluxograma do processo de negócio com links diretos para forms e tópicos de Help.
•Integração com Microsoft Project: botões Sync In, Sync Out e Enable Auto Sync Out no separador ADD-INS — só ativos se o checkbox "Project In Infor CloudSuite" estiver selecionado. Sync In traz novas tasks, recursos materiais/de trabalho e predecessors.
•Project Tasks — MS Project tab: Predecessors, Start/End Date (herdadas do General tab), e checkboxes Firm Start Date / Firm End Date para "congelar" datas e evitar que sejam recalculadas.
📋 Relatórios, utilitários e referências de journal (Apêndices) ▶
•Relatórios mais usados (Master Explorer > Modules > Project > Reports): Cost to Complete Log, Indented WBS Cost, Invoice/Revenue Milestone Progress e Nominated Milestones, Project Margin Analysis, Project Transactions, Project Variances, Project WIP Valuation (+ by Account), Packing Slip / Pre-Ship Packing Slip / Advance Ship Notice, Project Change Order Detail, Project Purchase Order Commitments, Unposted Labor Transactions, WBS Percent Complete.
•Utilitários: Roll Up Project Cost (recalcula custos/receitas do projeto com base em várias opções) e Project Roll From Forecast (copia valores forecast para os budget cost codes).
•Referências de journal no Project Control Ledger Distribution Journal: PRJ MTL (Project Resource Transaction), PRJ ADJ (Project Adjustment Transaction), PRJ LBR (Project Labor Transaction), JCLS PRJ (job fechado com variâncias WIP), JFIN PRJ (item de job parcialmente terminado e movido para inventário sem completar o job), JOL PRJ (labor de job postado), JOM PRJ (material de job postado), JMUV PRJ (variâncias de uso de material em standard costing), JFMO PRJ (variâncias de fixed material overhead).
•Project Change Orders: só disponível se Track Changes estiver ligado no projeto (e "Tracking" ativo no Project Types). Regista Change Number, Change Status (Opened/Finalized/Printed), data e utilizador da última alteração. Relatório: Project Change Order Detail Report.
💡 Pontos frequentemente testados: fórmulas de % Complete e Cost to Complete; os 3 métodos de WIP Relief; a diferença entre Post Project Invoice Milestones (só relatório) e a postagem real de Invoices/Credit Memos; e o facto de o shipping de recursos de projeto não gerar lançamentos contabilísticos.
